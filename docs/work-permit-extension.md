# 실제 작업허가서 확보 시 확장 경로

> **현재 상태: 실제 작업허가서를 확보하지 않았다.**
> YardGuard MVP는 저장소에 포함된 합성 데이터(`data/`)만 사용한다. 이 문서는 실제 문서를 확보했을 때
> 어떤 순서로 확장할 수 있는지에 대한 **계획**이며, 아래 기능 중 구현된 것은 없다.

## 1. 원칙

1. 실제 작업허가서를 확보하기 전에는 합성 데이터로만 개발·검증한다.
2. OCR이나 LLM이 뽑아낸 값을 **곧바로 위험판정에 사용하지 않는다.** 담당자가 확인·수정한 값만 규칙 엔진에 들어간다.
3. 위험 판정은 어떤 확장 단계에서도 결정론적 규칙 엔진이 수행한다.
4. 실제 문서와 그 파생물은 저장소에 커밋하지 않는다.
5. 어떤 단계에서도 산출물은 검토 보조정보이며, 작업허가 승인이나 법적 적합성 판정을 대체하지 않는다.

## 2. 비식별화 절차 (문서 반입 전)

문서를 개발 환경에 들이기 전에 다음을 제거·치환한다.

| 항목 | 처리 |
|---|---|
| 작업자·감독자·승인자 성명, 서명, 사번, 연락처 | 삭제 또는 `PERSON_01` 형태로 치환 |
| 협력업체명, 사업자번호 | `VENDOR_01` 치환 |
| 선박명, 호선번호, 선주명 | `HULL_01` 치환 |
| 실제 구역·블록 코드 | 프로젝트 공통 매핑표로 치환(`A_BLOCK_1` 등) |
| 사진, 도면, QR·바코드 | 제거 |
| 문서번호, 허가번호 | 해시 또는 순번으로 치환 |

- 치환 매핑표는 저장소가 아니라 회사 내부 접근통제 저장소에만 둔다.
- 비식별 처리 담당자와 처리 일자를 기록한다.
- 비식별 결과는 최소 1인이 교차 확인한다.

## 3. 문서 보관과 접근권한

- 원본(식별정보 포함)은 회사 내부 시스템에만 보관하고 개발 환경으로 복사하지 않는다.
- 비식별 문서는 별도 저장소(예: `data_private/`)에 두고 `.gitignore`로 제외한다.
- 접근권한은 최소 인원으로 제한하고, 반입·삭제 이력을 남긴다.
- 목적 달성 후 보관 기한을 정해 폐기한다.

## 4. 단계별 확장 경로

```
① 문서 텍스트화 → ② 서식 매핑 → ③ LLM 구조화 → ④ 담당자 확인 → ⑤ WorkItem 변환 → ⑥ 규칙 검사 → ⑦ 외부 일정 연동
```

### ① PDF·이미지 텍스트화 (OCR)

- 입력: 비식별 처리된 PDF 또는 스캔 이미지
- 처리: 디지털 PDF는 텍스트 레이어 추출, 스캔본은 OCR
- 산출: 페이지·좌표 정보를 가진 텍스트 조각
- 원칙: **OCR 결과를 그대로 판정에 사용하지 않는다.** 신뢰도가 낮은 영역은 원문 이미지와 함께 담당자에게 보여 준다.
- 붙일 위치: `backend/app/services/permits/`(신규)

### ② TemplateMapper — 회사별 서식 → 공통 초안

- 회사·양식마다 항목 위치와 명칭이 다르므로, 서식별 매핑 정의를 데이터로 관리한다.
- 산출: 공통 구조 `PermitDocumentDraft`(허가번호, 작업내용, 구역, 시간, 위험물질, 설비, 안전조치, 승인상태)
- 새 서식 추가는 코드 수정이 아니라 매핑 정의 추가로 처리한다.

### ③ LLM 구조화

- 기존 `LLMAdapter` 인터페이스(`backend/app/llm/base.py`)를 그대로 사용하고, 허가서용 프롬프트와 출력 스키마만 추가한다.
- 현재와 동일한 원칙: 명시된 사실만 추출, 없는 값은 `null`, 위험도·허가 가능 여부 판단 금지.
- 응답은 Pydantic으로 재검증하고, 허용 구역·enum·시간 형식을 통과하지 못하면 저장하지 않는다.

### ④ 담당자 확인 (필수 단계)

- 화면에 **원문 근거 ↔ 추출값**을 나란히 보여 주고 수정할 수 있게 한다.
- 필수 필드(작업종류, 구역, 시작·종료시각) 누락 시 저장을 막는다.
- 확인자, 확인 시각, 수정 이력을 남긴다.
- 이 단계를 건너뛰는 자동 저장 경로는 만들지 않는다.

### ⑤ WorkItem 변환

- 확정된 값만 기존 `WorkItem` 스키마로 변환한다. `source_type`에 `PERMIT`을 추가한다.
- 변환 시 기존 검증(표준시간대 필수, `end_at > start_at`, 등록된 구역)을 그대로 적용한다.
- 허가서 원문 식별자는 `external_id`에 비식별 형태로만 보관한다.

### ⑥ 규칙 검사

- 규칙 엔진(`backend/app/domain/rules.py`)은 변경하지 않는다. 입력 경로만 늘어난다.
- 회사별 작업허가 기준은 `data/rules.json`과 같은 형식의 규칙 카탈로그로 옮기고, 다음을 반드시 채운다.
  - 판정 조건, 등급, 경보 메시지, 권고 확인사항, 근거(사내 기준 문서 또는 법령 조문), 버전
  - 안전담당자의 검토 결과(`reviewed`)와 검토자·검토일
- 규칙은 버전으로 관리하고, 승인되지 않은 규칙은 `enabled=false`로 둔다.

### ⑦ 외부 일정 연동

- 전자 작업허가 시스템이나 공정관리 시스템에서 일정이 바뀌면 해당 작업만 갱신하고 전체를 다시 검사한다.
- 연동 어댑터는 읽기 전용으로 시작한다. YardGuard가 외부 시스템의 허가 상태를 바꾸지 않는다.

## 5. 평가 데이터 (과거 사고·아차사고 자료가 있을 때)

- 사고·아차사고 기록이 있으면 **규칙 평가용 라벨**로만 사용하고, 예측 모델 학습에는 사용하지 않는다.
- 사용 전 개인정보와 업체 식별정보를 제거한다.
- "이 규칙이 과거 사례를 걸러냈는가"를 확인하는 회귀 세트로 만들고, 결과는 규칙별 적중·미탐·오탐으로 기록한다.
- 표본이 적으면 통계적 성능 주장을 하지 않는다.

## 6. 실제 데이터와 합성 데이터 분리

```
data/           합성 데이터 (커밋 대상)
data_private/   비식별 실제 데이터 (커밋 금지, .gitignore 처리)
evaluation/     합성 평가 문장 (커밋 대상)
evaluation/results/  실행 결과 (커밋 금지)
```

- 코드에서 두 경로를 `DATA_DIR` 환경변수로 분리하고, 실제 데이터 경로를 기본값으로 두지 않는다.
- 테스트는 항상 합성 데이터로 실행한다.
- 실제 데이터가 필요한 검증은 별도 환경에서 수동으로 수행하고, 결과 요약만 문서로 남긴다.

## 7. 현장 적용 전 필요한 검증 단계

1. 회사 작업허가 절차와 규칙 카탈로그 대조(안전담당자 검토·승인)
2. 실제 구역 도면 기준으로 인접관계 정의 검증
3. 비식별 문서 표본으로 OCR·구조화 정확도 측정, 담당자 수정률 기록
4. 규칙별 오탐·미탐 검토와 임계값 조정
5. 현장 파일럿(읽기 전용, 기존 절차 병행)
6. 운영 기준 수립: 규칙 변경 승인 절차, 로그 보관, 접근권한, 장애 시 대체 절차
7. 법적 검토: 결과물의 성격(검토 보조정보)과 책임 범위 명시

이 검증을 통과하기 전에는 어떤 결과도 작업허가 승인이나 작업중지 판단의 근거로 사용하지 않는다.
